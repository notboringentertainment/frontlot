# Plan D10: Look locks — where visual identity becomes canon and how it reaches OpenMontage
_Drafted by Claude for Codex review, 2026-08-26. Follows the claudex-loop Phase 2 protocol; MAX_ROUNDS=5._

## Goal
Give the four-stage story workflow (PitchStudio → story-wayfinder → Buzz → WriterOS) one owner for a character's or location's visual identity, so that by the time a project reaches OpenMontage's `visual_bible` stage every cast entity has a ratified, structured "look spec" the pipeline can prompt from — with no invention by the pipeline (canon-explicit-only rule) and no new canon store. Found on the Bloodless pilot 2026-08-25: canon ingest produced 66 locks, 12 characters, 5 locations, and **zero** statements of anyone's appearance (blocking question q-019).

## Decision D10 (Ben, 2026-08-26): looks are wayfinder tickets
Story-wayfinder decides (the ticket is where the look is written and argued); a look becomes canon only through the ratification defined in D12 (a signed human receipt bound to the look's hash); WriterOS shows ratified looks as a dynamically rendered annex; OpenMontage consumes them through one ingestion routine. PitchStudio contributes at most a non-canon *type* note.

## The look spec (one strict, versioned shape, used end to end)
`look_spec` is a JSON-Schema `oneOf` on `entity_kind` (character | location), version `"1.0"`, bounded fields, shared by reference between repos (source of truth: `OpenMontage/schemas/look_spec.schema.json`; WriterOS vendors a copy with a hash check in tests). Key = `(entity_kind, entity_id)`, unique per project.
```
common:  version, entity_kind, entity_id (the BARE canon_packet id, unchanged; the look KEY is the pair
         (entity_kind, entity_id) — ids are never rewritten, finding R2#3), source_ticket_ref
         ({id} for new tickets with `id:`; {path, content_sha256} for legacy tickets — finding R2#7),
         fictional_subject_attestation: true (writer attests no real person is depicted or intended),
         minor: false (looks for minors are refused for generation),
         prompt_safe_description (20–80 words, present tense), continuity_risks[1..12],
         negative_lines[0..12], spoiler (bool), depends_on[] (ticket ids, derived from blocked-by),
         shape_only (bool: direction locked, details open — never sufficient for generation)
character: age_band (enum), build (enum + note), hair, distinguishing_marks[0..8],
           default_wardrobe {pieces[1..8]}, wardrobe_variants[0..6] {name, when},
           props[0..6], era_and_class_signals, heritage_note (optional, writer-stated only; agents never fill it)
location:  establishing_view, time_of_day_default (enum), palette_anchors[3..4] (named colors),
           architecture_or_terrain, dressing[0..10], weather_or_light_rules
```
No `status: ratified`, no `source_hash`, no `supersedes` INSIDE the block: the digest `look_hash` = sha256 of the RFC 8785 canonical JSON of the validated payload (finding R2#2), and it lives only in the external envelope — the look_lock receipt — together with `supersedes_look_hash` (optional) and `promotion_refs[]` (finding R2#8). Ratification is never self-attested. Prompt text is never propagated verbatim into provider calls; a structured prompt builder assembles it from fields (escaping, provider-disallowed content check, no injection-shaped lines), while `source_hash` proves fidelity to the ratified block.

## Ratification: what "a ratified look" means
A look is ratified when **all** of these exist, and OpenMontage verifies all of them:
1. The wayfinder ticket is `type: grill`, `mode: hitl`, resolved, with exactly one valid `## Look spec` fenced block; its validated payload hashes to `look_hash`.
2. **An OpenMontage `look_lock` approval receipt for that `look_hash` — always.** (Signed, ledgered, minted only by gate_approve.py from a terminal.) WriterOS promotion (Slice B) is an upstream convenience that can pre-fill the gate request; it is not proof, because WriterOS promotion events carry no signature OpenMontage can verify (finding R2#4).
3. No later receipt for the same key supersedes it: unique active look per `(entity_kind, entity_id)`; a replacement receipt names `supersedes_look_hash`; reopening a ticket writes a tombstone request that, once approved, retires the active look until a new one is ratified.

## Approach (ordered per the simpler safe path)

### Slice A — schema, wayfinder tickets, a `look_lock` stage in OpenMontage (unblocks Bloodless; no WriterOS change)
0. **New pipeline stage `look_lock` between `proposal` and `visual_bible`** (finding R2#1): inputs `canon_packet` (stays 1.1 — canon ingest is unchanged) and `proposal_packet` (its `cast` names the entities that need looks); produces `look_packet` (new artifact: `{version, looks[]: {entity_kind, entity_id, look_spec, look_hash, receipt_id, source_ticket_ref}}`). The stage director creates the look tickets in wayfinder for the cast (D15 lazy fan-out lives here), waits for the writer to resolve them, ingests them, and requests a `look_lock` receipt per entity. `visual_bible` requires `look_packet`. No cycle: cast is decided in proposal, looks follow, sheets follow looks.
1. `OpenMontage/schemas/look_spec.schema.json` + Python validation (strict oneOf, bounds, key uniqueness, `shape_only` never generation-sufficient).
2. story-wayfinder skill: `area: look`; NEW tickets get an immutable `id:` field (format `wf-<8hex>`, assigned at creation); legacy tickets are never edited (their content hashes are memory keys) and are referenced by `{path, content_sha256}`; `blocked-by` keeps titles for humans; `depends_on` in the look block is derived from blockers (id when present, else path+hash), never typed. Filenames `look-character-<slug>.md` / `look-location-<slug>.md`. **Lazy fan-out:** charting does NOT create look tickets; it records candidate entities under `## Not yet specified` with `revisit: look`. Look tickets are created by an explicit "cast for production" session when a production cast is approved (the proposal_packet cast, or Ben's list), one per cast entity. Close rules in rubric: block must validate, `fictional_subject_attestation` true, `minor` false, spoiler flag set deliberately, blockers resolved.
3. `lib/look_ingest.py`: one shared ingestion routine used for every source (direct wayfinder tickets now; WriterOS export in Slice B): verifies ticket authority (grill+hitl+resolved), block validity, computes `look_hash`, verifies the look_lock receipt, uniqueness/supersession, spoiler propagation, prompt-injection scan (shared regex list vendored with a hash test). Output is the `look_packet` — canon_packet is NOT bumped (ids and the 1.1 branch untouched; finding R2#3). Version guards that read `== "1.1"` are left alone.
4. gate_approve.py gains kind `look_lock` (record = the validated payload; receipt binds `look_hash`, entity key, source_ticket_ref, optional `supersedes_look_hash`, `promotion_refs[]`). The look_lock director writes the request; Ben approves from a terminal.
5. Enforcement is a runtime invariant, not director prose (finding R2#5): (a) `write_checkpoint` for `visual_bible` with status `in_progress` (and `awaiting_human`/`completed`) runs `_check_look_packet`: every cast entity has an active look_lock receipt, non-`shape_only`, non-minor; trailer/teaser refuse `spoiler` cast; (b) governed visual calls (seedream, kling, seedance, title_card, poster_composite) REQUIRE `look_refs[] {entity_kind, entity_id, look_hash}` — a call may omit them only when it names a `shot_id` whose approved scene-plan record is `entity_free: true` (server-side lookup in the approved scene_plan checkpoint; the tool-call boolean alone is never trusted, R4#2) — and `visual_bible`-stage model calls can NEVER be entity-free (every sheet/hero/poster generation names its entity); `paid_call_context` verifies each look_ref against the active look receipt before any upload, binds `look_refs` into the signed generation receipt, and the prompt is produced by the structured builder from the look_spec — the visual_bible `approved_prompt_block` string contract is REPLACED by `prompt_recipe {look_hash, builder_version, fields_used[], rendered_sha256}`; asset-director's verbatim-copy rule is rewritten to 'rebuild from the recipe and verify rendered_sha256'; (c) completion-time validation retained. Rollout (R3#1, R4#1): every checkpoint carries `pipeline {name, version, manifest_digest}` (checkpoint schema addition; `write_checkpoint` fills it from the loaded manifest and refuses a manifest whose digest differs from the project's pinned tuple); the pin itself is a signed **`pipeline_migration` receipt** (kind added to gate_approve.py), and migration receipts form a **monotonic supersession chain** (each names `supersedes_receipt_id`; the loader accepts only the unique ledger tip, R5#1) — a downgrade is a new human-approved receipt that supersedes the tip, never a cache edit; `project.json.pipeline_manifest_version` is a cache verified against the tip. Legacy checkpoints are not rewritten (R5#2): the checkpoint schema gains a backward-compatible branch (tuple required for checkpoints written under a 1.2 manifest, optional before), and the 1.1 migration receipt externally binds each existing checkpoint's digest to the signed 1.1 manifest. Standalone validation reads the tuple from the checkpoint. Existing projects get a one-time `1.1` migration receipt minted through the gate. `pipeline_loader` resolves `pipeline_defs/authored-film@<version>.yaml`; `look_lock` exists only in 1.2.
6. visual_bible schema v1.1: each entity entry gains `look_ref {entity_kind, entity_id, look_hash, receipt_id}` and a `sheet_revision` (history is per revision; the entity id stays stable — finding R2#6). The sheet approval record includes `look_hash`. Enforcement at `visual_bible`, `assets`, and every downstream gate requires `look_ref.look_hash` == the current active look for that key. Look receipts carry an `action: activate | retire` (R3#4): `retire` (tombstone or supersession) is a signed receipt like any other. Checkpoints stay immutable (R4#3). Invalidation is **derived from the approval ledger on every validation** (R5#3): `get_latest_checkpoint`, `_enforce_stage_prerequisites`, and delivery recompute the set of invalidated checkpoints from active `retire` receipts; `projects/<slug>/invalidations.jsonl` is only a rebuildable cache whose completeness is verified fail-closed (missing/truncated cache → rebuild, never trust). Scope is conservative (R5#4): a retired look invalidates the `visual_bible` checkpoint(s) carrying that `look_ref` **and every completed checkpoint of every downstream stage** (script, scene_plan, assets, edit, compose) written after it, until each is re-approved; checkpoints written under 1.2 additionally bind `predecessors[] {stage, checkpoint_digest}` so a later slice can narrow invalidation to exact descendants. Invalidated checkpoints are treated as not completed (cannot be resumed past, cannot satisfy `required_artifacts_in`, listed with the retiring receipt id). Approving a new sheet revision writes a new checkpoint; the invalidated one remains on disk as history.
7. Reference provenance (R2#9, R3#3): `canon_packet.reference_assets` / `reference_assets_needed` are advisory only. Governed image tools reject remote reference URLs outright; every local reference must have a verified generation receipt whose lineage is itself receipted (recursive check over `input_asset_ids` / `references_applied`, bounded depth, cycle-safe); the tool records the exact `references_applied` lineage in its own signed receipt (Seedream gains this field — it currently omits it). A reference with no receipted lineage is refused before upload with the real-person/unconsented message. The look_lock request shows the writer's `fictional_subject_attestation` and the refusal rule. Entity ids are unchanged in Slice A; cross-repo immutable ids are Slice C.

### Slice A′ — `headshots` stage and reference-image import (Ben's caveat, 2026-08-26; revised after Codex round 6)
Ben approved the plan with one caveat: a face must be approved before any sheet is generated, and the pipeline must ask whether he already has a reference image (generated elsewhere, or a real-person casting inspiration; JPEG/HEIC/PNG).

1. **When the question is asked.** "Do you have a reference image?" is asked **while the wayfinder look ticket is being drafted** (R6#1, R7#1): the wayfinder skill asks it in the look-ticket procedure; the writer resolves the complete `## Look spec` block in the ticket, including any type fields informed by a casting image. OpenMontage `look_ingest` hashes the resolved ticket as-is and never patches fields at approval time. The image import itself (the gate below) happens in `look_lock`, before ratification. Two answers:
   - `casting_inspiration` (a real person): imported through the gate (kind `reference_import`), stored under `canon/visual/casting-inspiration/` (outside `objects/`), **displayed to Ben only**. No model, director, or vision process ever receives the pixels or a description of the face (R6#2). Ben types the allowlisted type fields himself (age_band, build, era_and_class_signals, hair as a category); facial descriptors are not fields. The signed `reference_import` receipt binds `{origin_class, normalized_pixel_hash, attestation_text, attestation_receipt_id}` (R7#4); the project-wide **taint set** = every `casting_inspiration` hash in the approval ledger, derived from the ledger on every validation (any cache is fail-closed and rebuildable). A tainted hash can never be an `imported_synthetic`, never in a `reference_manifest`, never in lineage; `paid_call_context` refuses before upload; enforcement rejects any receipt whose lineage touches it; a later import of identical pixels under any other class is refused (R6#6).
   - `imported_synthetic` (generated elsewhere): imported through the gate with the attestation "machine-generated, depicts no real person"; generation receipt `generator_kind: imported` with `origin_tool`, `attestation_receipt_id`, normalized pixel hash. A legitimate lineage root. The `imported` provenance branch is added everywhere `model`/`local` are validated today — receipt creation, `ImageRef.provenance` oneOf, provenance comparison, recursive lineage, local-composition checks (R6#5).
2. **New stage `headshots`** between `look_lock` and `visual_bible`, scoped to `proposal.cast.character_ids` only (R6#8; location references are handled inside `visual_bible`). Inputs `look_packet`, `proposal_packet`. One discriminated artifact `headshot_packet` with `state: pending | approved` variants (R7#2, satisfies the manifest output contract at both `awaiting_human` and `completed`): `pending` carries per character up to 4 candidate ImageRefs (generated from the `prompt_recipe`, or the single `imported_synthetic` hero if Ben supplied one) and no hero; `approved` carries per character `{entity_kind, entity_id, look_ref, hero: ImageRef, origin: generated | imported_synthetic, import_receipt_id?, normalized_pixel_hash, approval_receipt_id, candidates_rejected[]}`. Completion requires `state: approved`. One character at a time; Ben picks one or rejects all (regeneration with a logged note). Gate kind `headshot` is a **selection gate** (R7#3): `gate_approve.py` gains a candidate-selection mode — it reads the `pending` packet from the `awaiting_human` checkpoint, verifies each preview file's bytes against the candidate asset hashes and candidate membership, enumerates them, accepts `1..N` or `reject-all` (+ note) from the human, and **constructs the signed record itself** `{entity key, look_hash, chosen asset_id, normalized pixel hash, origin, import receipt id, prompt_recipe hash, candidates_checkpoint_digest}` — the agent never authors the approval record. Headshot receipts form a per-entity monotonic supersession chain (R7#5): a replacement names `supersedes_receipt_id` and retires the previous atomically; consumers accept only the unique ledger tip.
3. **Sheets derive only from the approved hero** — enforced, not prose (R6#4): every `visual_bible` character generation call requires `headshot_ref {entity_id, asset_id, approval_receipt_id}`; the tool verifies asset + receipt against the current `headshot_packet` before upload and binds `headshot_ref` into its generation receipt; enforcement rejects a sheet ImageRef whose receipt lacks a matching `headshot_ref`. Rejected candidates keep their receipts as history but cannot satisfy this check. The former hero sub-gate inside `visual_bible` is removed.
4. **Invalidation** (R6#7): look receipts (`activate|retire`) invalidate `headshots` onward; headshot receipts (`activate|retire`) invalidate `visual_bible` onward. Both derived from the ledger per Slice A rule.
5. **Import normalization** (R6#9), one deterministic routine for all three formats: decode (HEIC/HEIF via `pillow-heif`; missing library → explicit install error, never a silent skip; multi-frame/animated inputs rejected; decode size/pixel limits enforced); apply EXIF orientation; convert to sRGB 8-bit (ICC applied then dropped); alpha: flatten onto white for JPEG/HEIC sources, preserve for PNG; re-encode PNG with fixed encoder parameters and **no** metadata chunks (EXIF/GPS/ICC/XMP/text); hash the result; temporary source bytes deleted on every path including failure; the original file is never copied into the project. Tests: identical pixels across JPEG/HEIC/PNG hash identically; rotated EXIF input lands upright; GPS/EXIF absent in output; multi-frame rejected; oversize rejected.
6. Enforcement additions: `headshots` completion requires one approved hero per `cast.character_ids` entity with `look_ref.look_hash` current; an `imported_synthetic` hero must cite its import receipt; any lineage touching a tainted hash fails at every gate. D3 restated: every lineage root is a pipeline generation receipt or an attested `imported_synthetic` import; nothing else.
7. Tests as listed above plus: casting_inspiration in a reference manifest rejected before any network call; identical pixels re-imported as synthetic after a casting import rejected; sheet call without `headshot_ref` rejected; headshot required before sheet; rejected-all regenerate path logged.

### Slice C — cross-repo entity aliases and project migration
1. Entity ids are NEVER rewritten in any signed or referenced artifact (R3#5). Cross-repo linkage is an **alias approval**: each alias `{canon_id, writeros_id?, wayfinder_key?}` is a signed, ledgered receipt (kind `entity_alias`, minted via gate_approve.py) — never a plain append (R4#5). Uniqueness is enforced at approval and at every resolution: one canon_id per external id and vice versa, no remap (changing an alias requires a `retire` receipt on the old one plus a new approval). Resolution verifies the receipt signature + ledger every time. WriterOS gains a minimal locations collection so locations have ids to alias.
2. Project migration to manifest 1.2 is a signed `pipeline_migration` receipt, and for a project with completed visual work it is an atomic all-artifact step: new `look_lock` checkpoint, then a `headshots` checkpoint with one approved current headshot per cast character (selected through the selection gate from existing receipted heroes with complete lineage, or regenerated) before any sheet is accepted (R7#6), then **every reference-capable historical image whose signed generation receipt lacks complete `references_applied` lineage is refused and must be regenerated** (R4#4) — re-approval alone never launders unknown ancestry; only images with complete receipted lineage may be carried into a new `sheet_revision` for Ben's re-approval. Frozen/closed projects (The Understudy) are never migrated.

## Key decisions & tradeoffs
- **D10 Wayfinder owns looks.** Rejected: PitchStudio (permanent decision before constraining story facts exist); WriterOS free-text field (bypasses ratification); OpenMontage inventing looks.
- **D11 One strict shape (`look_spec` 1.0)**, fields not prose; prompts built from fields, never copied verbatim.
- **D12 Ratification = a signed OpenMontage `look_lock` receipt bound to `look_hash`**; never a field in the data; WriterOS promotion can pre-fill the request but is not proof. This is the sole authority statement in this plan.
- **D13 Missing/unratified look = checkpoint and generation-boundary failure** for manifests that declare the `look_lock` stage; older manifests unaffected until Slice C.
- **D14 Annex is dynamic, not stored** — no second canon copy on disk.
- **D15 Look tickets are created lazily from an approved production cast**, not fanned out at charting.
- **D16 Likeness/privacy:** writer attests fictional subject at ticket close; minors refused; heritage writer-stated only; every lineage root is a pipeline generation receipt or an attested `imported_synthetic` import; real-person images are `casting_inspiration` — local only, never uploaded, never in lineage; provider policy handled per model. Out of scope: proving a generated face resembles no one.
- **D17 Headshot before sheet (Ben, 2026-08-26):** a face is approved as its own stage before any sheet or shot spend. The reference-image question is asked during `look_lock` (before the look hash is sealed); real-person casting inspiration is seen by Ben only, never by a model, and is permanently tainted out of every lineage; generated-elsewhere images are attested imports that become lineage roots.

1. Wayfinder rubric/harness are the enforcement surface for skill behavior; the new `id:` field is additive. 2. The memory adapter today declares `approval: explicit` from placement/headers (verified) — hence D12. 3. Story Bible schema does not grow in Slice B (annex is rendered, not stored). 4. OpenMontage canon-director lists wayfinder resolved tickets as a source today; the WriterOS export path in Slice B is new and specified explicitly above. 5. No Buzz change. 6. `canon_enforcement.py` has exact-version guards (`== "1.1"`) that Slice A must relax with tests.

## Risks / open questions
- Ethnicity/heritage in a look spec: writer-stated only, optional, never inferred by any agent; the spec field exists so the writer can state it, and agents must not fill it.
- Real-person likeness: `prompt_safe_description` must not name or describe a real person (wayfinder rubric refuses at close; the OpenMontage prompt builder rejects known-person name patterns). Synthetic-only enforcement proves images were pipeline-generated; it cannot judge resemblance.
- Supersession cost: changing a ratified look after sheets exist invalidates sheets and every shot citing them; the plan accepts that by design.
- Two promotion paths (A receipt, B WriterOS) for the same hash are equivalent by design; a look promoted in both records both ids.
- Bloodless: only the approved trailer cast (≤4 characters, ≤4 locations) gets look tickets (D15); the pilot resumes after those are promoted via Slice A.

## Out of scope
Voice/casting of performers; LoRA training from looks; automatic look proposals by any agent (an agent may draft a Question, never an Answer); PitchStudio changes beyond the export heading; retrofitting looks for closed projects (The Understudy is frozen).
