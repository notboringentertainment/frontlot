# Plan D19: Sheet QC — machine-checked acceptance before a human is asked
_Drafted by Claude for Codex review, 2026-08-27. Follows the claudex-loop Phase 2 protocol; MAX_ROUNDS=5._

## Goal
Stop presenting defective character sheets to the human. On the Bloodless pilot (2026-08-26) the operator presented, in sequence, a turnaround with a cigarette in two portraits (a conditional prop rendered from the look spec), a turnaround with the shoes cropped, and a turnaround whose two "profiles" both faced left. Each was caught by Ben, not by the pipeline; each cost a round trip and $0.135. The director skill now carries an acceptance checklist (`skills/pipelines/authored-film/visual-bible-director.md`, "Sheet acceptance checklist"), but a checklist an agent reads is advice. D19 makes it a gate precondition: every sheet asset must carry a passing, receipted QC verdict from an independent vision judge before a `sheet` gate request can be constructed, and the generation loop regenerates on its own (bounded) before the human sees anything.

Out of scope: judging artistic quality or likeness (the human still approves identity); locations and posters (same mechanism later, separate checklists); replacing the human gate.

## Diagnosis (verified)
- Sheet views are produced by `SeedreamImage.execute` through `paid_call_context` with a builder-1.3 `prompt_recipe` (`tools/prompt_builder.py`), and are sealed by a generation receipt per asset (`lib/receipts.py`). Nothing between generation and the gate inspects pixels.
- `scripts/gate_approve.py::_construct_character` verifies each ImageRef's bytes, hash, lineage and look binding (`_verify_image_ref`) and then signs `character_approval_record`. It cannot know whether panel 3 faces right.
- The operator currently drives generation with a one-off script (`scripts/bloodless_sheet_ace.py`, project-specific, argv roles) and builds the draft + gate request from a scratch file. There is no reusable, project-agnostic "make this entity's sheet" command, so the retry loop lives in chat.
- Vision-capable providers with keys already in `.env`: `OPENAI_API_KEY` (used by `tools/video/sora_video.py`), `GOOGLE_API_KEY` (used by `tools/video/gemini_omni_video.py`, `tools/graphics/google_imagen.py`). No Anthropic key. FAL hosts VLMs too but our FAL path is image/video generation only.

## Design

### D19.1 Checklists are versioned data, not prose
`lib/sheet_qc/checklists.py` defines `CHECKLIST_VERSION = "1.0"` and one checklist per sheet role. Each item: `id`, `question` (yes/no, phrased so YES = pass), `severity: fail | warn`, and optional `evidence_field` naming the look_spec field the judge is given (e.g. `default_wardrobe.pieces`). Turnaround items (all `fail` unless noted):

| id | question |
|---|---|
| panels_7 | Exactly seven panels: four full-body over three portraits? |
| profiles_opposite | Do the two full-body profile panels face opposite directions (one nose to the left edge, one to the right)? |
| portraits_opposite | Do the two profile portraits face opposite directions? |
| shoes_visible | Are both shoes fully inside the frame on every full-body panel? |
| hands_empty | Are the hands empty in every panel, with nothing held and nothing at the mouth? |
| wardrobe_complete | Is every listed wardrobe piece visible where the angle allows? (given `default_wardrobe.pieces`) |
| head_height | Same head height across the full-body row and same facial scale across the portraits? (warn) |
| one_light | One consistent light direction across all panels? (warn) |
| single_subject | Exactly one person, the same person, in every panel? |
| no_text | No text, watermark or logo? |

Expressions items: `grid_2x3`, `head_shoulders_only`, `realism_matches_hero` (given the hero image as a second input), `mouth_clear` (nothing in or at the mouth), `no_hands_props`, `six_distinct` (warn), `single_subject`, `no_text`. Wardrobe items: `variants_side_by_side`, `full_body`, `pieces_visible` (given pieces), `single_subject`, `no_text`.

The checklist hash (`record_sha256` of the item list) is part of every verdict so a verdict cannot be replayed against a changed checklist.

### D19.2 The judge is a paid tool with a receipt, like every other provider call
`tools/qa/sheet_judge.py` (`SheetJudge(BaseTool)`), provider-neutral interface, first provider **OpenAI Responses API with image input** (model pinned in `project.yaml` `qc.judge_model`, default `gpt-5.5`; verified by a smoke probe before the build counts on it, see Assumptions). Input: `{project_dir, asset_id, role, look_refs, checklist_version, hero_asset_id?}`. It:
1. Loads the image **only from `canon/visual/objects/<asset_id>.png`** (never a path the caller supplies; casting-inspiration images are structurally impossible to send because they live elsewhere and the judge resolves by asset_id in the objects vault only).
2. Builds the judge prompt from the checklist + the active look's `default_wardrobe.pieces` and `hair`/`age_band` (from the signed active look via `lib.look_ingest.active_look_for`, never from caller text). Fixed system prompt: answer each item `yes|no|unsure` with a ≤20-word note; JSON only; `unsure` counts as `no`.
3. Calls the provider with `response_format` JSON schema, temperature 0, `max_output_tokens` ≤ 600, one retry on transport error, **no retry on a parsed answer**.
4. Returns a `qc_verdict` (schema `schemas/artifacts/qc_verdict.schema.json` v1.0): `{version, asset_id, role, checklist_version, checklist_sha256, look_hash, judge {provider, model, prompt_sha256, response_sha256}, items[{id, answer, note}], verdict: pass|fail, warnings[], cost_usd, judged_at}`; `verdict` is computed by code from item answers and severities, never taken from the model.
5. Runs inside `paid_call_context` with `stage: "visual_bible"`, `asset_role: "qc"`, cost reservation and a **generation-style receipt of kind `qc`** appended to the project's generation-receipt chain (`lib/receipts.py` gains `record_qc_verdict`): the receipt binds `asset_id`, `checklist_sha256`, `look_hash`, `response_sha256`, `verdict`. Same one-use, WAL, ledger and chain rules as image receipts.

The judge never writes canon, never mints approvals, never touches checkpoints. Its output is data.

### D19.3 The sheet gate requires a passing verdict per sheet asset
- `lib/sheet_qc/verify.py::require_qc_pass(project_dir, entry)` — for every role in `sheet_roles(entry)`: find the newest `qc` receipt for `(asset_id, role)` whose `checklist_version` is current and whose `look_hash` is the active look; require `verdict == "pass"`. Missing, stale-checklist, wrong-look or failed verdict → `QCRequired` error naming the role and the failing item ids.
- `scripts/gate_approve.py::_construct_character` calls `require_qc_pass` before constructing the record; the printed evidence gains one line per role: `turnaround: QC pass (checklist 1.0, receipt <id>, warnings: head_height)`.
- `lib/canon_enforcement._check_visual_bible_v12` calls the same function when a character entry is written with `status: approved` (belt and braces: an approved entry without QC receipts is invalid even if a receipt somehow exists).
- **Human override, explicit and recorded:** `gate_approve.py --accept-qc-failure <role>:<item_id>` lets Ben approve despite a failed item (e.g. the judge is wrong). The record gains `qc_overrides[{role, item_id, qc_receipt_id}]`, so the signature covers the override and the ledger shows who accepted what. No override for a *missing* verdict: the judge must have run.

### D19.4 One command makes a sheet, retries itself, and stops at the gate
`scripts/sheet_run.py --project <slug> --entity <id> [--roles turnaround,expressions] [--max-attempts 3] [--open]` replaces the pilot's one-off script. Per role, sequentially (D18 one-face-at-a-time is per entity; roles of one entity may run in order):
1. Generate via the governed Seedream path (same inputs as today, project-agnostic: active look, active headshot, palette from proposal).
2. Judge. On `pass` keep; on `fail` log the failing items and regenerate with the same recipe (no prompt mutation by the loop; prompt fixes are builder changes under version bump). Stop after `max_attempts`; the role is then `blocked` and the run exits non-zero listing the persistent failures. Never present a failing sheet.
3. Budget: the loop reserves `attempts × price` up front against the project cap and refuses to start if it would exceed it; every attempt's asset and receipt remain in the vault (auditable spend, nothing deleted).
4. On all roles passing: write the `visual_bible` checkpoint (`awaiting_human`, entry `status: draft`, next `sheet_revision`), write the `sheet-<entity>-<n>` gate request with `qc_receipt_ids`, print the approval command and, with `--open`, open the passing images.

The run is resumable: existing passing verdicts for the current look + checklist are reused, so a crash after the turnaround passed does not re-buy it.

### D19.5 Regenerating the operator's own judgement
The director skill keeps the human-readable checklist but its instruction changes to: "run `scripts/sheet_run.py`; do not hand-generate sheet views; present only what the run produced." The agent's eyes remain a second check, not the first.

## Approach (build order)
1. `schemas/artifacts/qc_verdict.schema.json`; `lib/sheet_qc/checklists.py` (+ hash, tests).
2. `lib/receipts.py`: `record_qc_verdict`, `find_qc` (newest per asset/role), chain/ledger tests mirroring generation receipts.
3. `tools/qa/sheet_judge.py` + OpenAI provider adapter + fixture-recorded contract test (`tests/fixtures/providers/openai-responses-vision.json`) + refusal tests (path outside vault, casting dir, missing look).
4. `lib/sheet_qc/verify.py::require_qc_pass`; wire into `gate_approve.py` and `canon_enforcement`; `--accept-qc-failure` with record binding; tests for missing/stale/failed/override.
5. `scripts/sheet_run.py` (project-agnostic; invented-name fixtures only); dry-run mode that uses a fake judge; budget refusal test; resume test.
6. Skill doc update; PLAN review log; smoke on Bloodless: rerun Ace's two roles through `sheet_run.py` (expected: both pass first try, ≈$0.20 generation + judge cost), then approve revision 3 at the gate. Sebastian starts only after that.

## Key decisions & tradeoffs
- **Judge = external model, not the operator.** The failures were the operator's own perception. An independent judge with a fixed checklist and JSON answers is cheaper than a human round trip and does not tire. Risk: judge error; mitigated by `unsure→no`, warn-tier items, and the explicit recorded override.
- **Verdict is a receipt, not a checkpoint field.** Verdicts must be unforgeable by the agent that wants the gate to open, so they go through the same signed chain as generation receipts and are found by `(asset_id, role, look_hash, checklist_sha256)`, never trusted from a JSON the agent wrote.
- **Regeneration does not mutate the prompt.** A loop that rewrites prompts to please a judge drifts from the ratified look and defeats `prompt_recipe`. Persistent failure is a builder bug and gets fixed under a version bump, as happened three times today.
- **OpenAI first, provider-neutral interface.** Key exists; Responses API accepts images and JSON schema output. Gemini adapter is a follow-up if OpenAI refuses faces or costs more than expected.
- **No override for missing verdicts.** Otherwise "skip QC" becomes the default path under time pressure.

## Assumptions
1. OpenAI Responses API with `gpt-5.5` accepts a 2560×1600 PNG plus a hero PNG as `input_image` and honours `text.format: json_schema`; per-call cost well under $0.05. — source: sora_video.py uses the same key; model capability to be verified by a $0.05 probe in step 3 before anything depends on it. If it fails on photoreal faces (policy), fall back to Gemini via `GOOGLE_API_KEY`.
2. Judges answer geometric questions (facing direction, cropped shoes, item in hand) reliably at temperature 0; likeness/realism questions are weaker, hence `warn` tier and hero image as second input. — source: general VLM behaviour; measured on the three real failures from 2026-08-26 as regression fixtures (the failing images are still in the vault: `4b1b3a4f…` cigarette, `16dadc8c…` cropped shoes, `d3e77a3b…` same-direction profiles; expected: fail on the right item each; `0b09fb34…` expected pass).
3. `paid_call_context` can host a non-image provider call with a new receipt kind without changing the chain format. — source: `lib/receipts.py` receipt envelope is kind-tagged; to confirm in step 2.
4. The Bloodless project cap ($100) has room; judge cost per sheet ≈ $0.02–0.10.

## Risks / open questions
- R1: The judge may flag true positives as `unsure` on subtle items (wardrobe piece hidden by angle) → wasted regenerations. Mitigation: `wardrobe_complete` phrased "where the angle allows"; cap attempts; warn tier for subjective items.
- R2: Two-image input (hero + sheet) doubles tokens; if too costly, `realism_matches_hero` becomes single-image with a text description.
- R3: Chain growth: 3 attempts × 2 roles × 2 receipts each per entity. Acceptable; the chain is append-only JSONL.
- Q1: Should `warn` items ever block? Proposal: no, but they are printed at the gate so the human sees them.

## Out of scope
Location and poster QC (same mechanism, separate checklists, later); judging identity likeness as pass/fail; automatic prompt repair; any change to who approves canon.
