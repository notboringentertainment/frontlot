# Plan D20: `look_run.py` and `headshot_run.py` — the two steps before a sheet become commands
_Drafted by Claude for Codex review, 2026-08-28. Follows the claudex-loop Phase 2 protocol; MAX_ROUNDS=5. Revision 7 after Codex rounds 1–6 (round 6 authorised by Ben; its three items folded in — see REVIEW-LOG)._

## Goal
After D19 the sheet step is one governed command (`scripts/sheet_run.py`): generate, judge, retry within a signed cap, stop at the gate. The two steps before it are still hand-driven: the look ticket is ingested and its `look_lock` request written by an operator in chat, and headshot candidates (or a reference import) are produced by ad-hoc scripts, exactly the shape that produced the 2026-08-26 defects. Ben's ruling (2026-08-28): the deliverable is the workflow, project-agnostic, not Bloodless assets. D20 makes the whole per-character path three commands, each stopping at exactly one human gate, with nothing project-specific in code:

```
look_run.py     --project <slug> --entity <id> [--casting <file>]   → (casting import gate) → look_lock gate
headshot_run.py --project <slug> --entity <id> [--import <file> --origin-tool <name>]
                                                          → reference_import gate (if importing) → headshot selection gate
sheet_run.py    --project <slug> --entity <id>            → sheet gate (D19)
```

Out of scope: locations (same pattern later), the writer's authorship of the look ticket (that stays in story-wayfinder), any change to who approves canon, judging likeness.

## Diagnosis (verified 2026-08-28)
- `lib/look_ingest.py` already has `parse_look_ticket`, `look_lock_request`, `active_look_for`, `verify_look_refs`; the operator called them by hand for Ace. No command wraps them.
- `lib/reference_import.py` has `stage_reference_upload`, `prepare_reference_import` (writes the `reference_import` gate request, drops caller metadata), `finalize_reference_import`, `imported_image_ref`; `lib/headshots.py` has `headshot_request` (selection gate request with no record) and `headshot_record`; `scripts/gate_approve.py` selection mode (`headshot_candidates`, `_enforce_candidate`) rebuilds the record from the pending `headshot_packet`. Ace's import and single-candidate packet were assembled by hand.
- `headshots-director.md` specifies the intended flow (imported hero = single candidate; else up to 4 generated candidates from `tools/prompt_builder` role `hero` with `look_refs`; reject-all regenerates with a logged note; approved packet rewritten per character under D18). None of it is a command.
- D19 infrastructure is reusable as-is: QC stream (`lib/qc_receipts`), policy bundle (`lib/sheet_qc/policy`), `SheetJudge`, `qc_call_context`, attempt rows and the signed cap, `qc_override`, `verify_series_against_receipt`. The qc_verdict schema and `SheetJudge` restrict `role` to sheet roles.
- `tools/prompt_builder.py` has a `hero` framing ("head and shoulders portrait, neutral expression, facing camera") and `builder_policy_sha256()`; Seedream `text_to_image` is the governed generation path for candidates (no reference image exists yet).

### D20.1 `scripts/look_run.py` — ticket to gate, no spend
`look_run.py --project <slug> --entity <id> [--kind character|location] [--dry-run]`
1. Preconditions: any verified config version ≥ 1.0 (1.0, 1.1, 1.2 — no paid call, R3#2), pin ≥ 1.2, `wayfinder_root` in config, run lease.
2. Locate the resolved ticket for the entity under `<wayfinder_root>/wayfinder/resolved/` by `entity_id` in its `## Look spec` block (never by filename); refuse if the ticket is not resolved, has no answer, or more than one ticket claims the entity.
3. `parse_look_ticket` → validated payload (schema + injection scan + `depends_on` derived from `blocked-by`, existing rules); `look_hash`.
4. **Order of operations** (R3#3, R4#1): if run state exists for the entity, the command resumes/finishes ONLY the exact `request_id` it names (a `done/` request with any other id is history and never consulted), then atomically clears that run state in the same checkpoint write that records the outcome; only a genuinely new run (no run state) is subject to the guard: if an active look exists for the key, refuse unless `--supersede`, in which case the request carries `supersedes_look_hash` (existing envelope field).
5. **Run state before every request** (R5#1): write `look_lock` checkpoint `metadata.run_state[entity] = {mode: look_lock, revision, request_id: f"look-{entity}-{revision}", look_hash, expected_kind: look_lock}` into the `look_lock` checkpoint, compute its digest, then write the gate request via `look_lock_request` with `source_checkpoint_digest`; print the approval command; `--dry-run` prints what would be requested and writes nothing. The post-casting transition (step 7) ends by doing exactly this.
6. **Recovery states, exhaustive** (R5#2) — on any invocation with run state present, by what exists for its `request_id`: (a) no request file and no receipt → the crash window between state and publish: re-verify the staged hash / look_hash against the state and republish the same request id; (b) pending → print the command and exit; (c) in `done/` with a verified receipt of `expected_kind` matching the state's hash → finish, **mode-specific** (R6#2): `mode: look_lock` → write/refresh the `look_lock` checkpoint `in_progress` with the partial packet (`build_look_packet`, existing) and clear the state in the same write, so `headshots` can start (D18); `mode: casting` → `finalize_reference_import`, then in the same checkpoint write replace the state with a new `{mode: look_lock, …}` tuple and publish the look request (step 5), i.e. the casting→look transition is one atomic step; (d) in `declined/` → consume it (log the note, clear state), exit with "declined: edit the ticket and rerun"; (e) anything else (a request with another id's content, a receipt for a different hash) → fail closed with the mismatch named. Idempotent.
7. **`--casting <file>`** (R1#9, moved here from headshot_run per D10: the casting question belongs to look drafting, before ratification): `stage_reference_upload` (the writer's original is copied, never consumed — R1#10) → `normalize_reference_import` → **run state** `look_lock` checkpoint `metadata.run_state[entity] = {mode: casting, revision, request_id, normalized_pixel_hash, expected_kind}` in the `look_lock` checkpoint metadata → digest → `publish_import_request(origin_class=casting_inspiration, entity_id=<entity>, request_id=f"casting-{entity}-{revision}", source_checkpoint_digest=<digest>)` (R4#2) with the same no-overwrite / cross-entity-hash refusals as Mode A (R3#5) → `reference_import` gate request bound to the checkpoint digest; stop. The next invocation resumes only that tuple: finds the approved `reference_import` receipt for that hash, runs `finalize_reference_import` (the one sanctioned read: hash check + move into `canon/visual/casting-inspiration/`), clears the run state, and only then may the entity's `look_lock` request be written (R2#5). The command refuses `--casting` once the entity's look is ratified. The prohibition is precise: **no model, director, judge, prompt, receipt or ticket text ever receives the image or a description of it**; the pipeline's own integrity reads (finalize, taint hashing) are allowed and are the only reads.

Nothing here decides appearance; the writer did that in the ticket. The command only moves a resolved ticket to the gate and records the ratification in the checkpoint.

### D20.2 `scripts/headshot_run.py` — one approved face per character
`headshot_run.py --project <slug> --entity <id> [--import <file> --origin-tool <name>] [--candidates N≤4] [--replace] [--finish] [--open]`

Preconditions (this command's own validator; neutral helpers from `lib/run_common.py`): registered project, verified 1.2 config with `qc.max_hero_attempts`, pin = 1.4 (**except `--grandfather`, which is the one mode allowed under pin 1.3**, R3#4), run lease, `resume_check`, active look for the entity (else "run look_run first"). **Finish/resume before guards** (R3#3, R4#1): if run state exists for the entity, the command finishes or resumes ONLY the request id it names (step 8), clears the state atomically with the outcome write, and exits; `done/` requests are never scanned; only a new run is subject to: no active headshot for the entity unless `--replace` (which makes the eventual receipt carry `supersedes_receipt_id`, existing mechanism, and prints the downstream-invalidation cost before anything runs).

**Mode A — import (`--import`)**. The file (JPEG/HEIC/PNG) is the writer's own generated image of the character:
1. **Normalize, persist, then publish** (R3#5, R4#2): `prepare_reference_import` is split into `normalize_reference_import(...) → (normalized hash, staged PNG, record)` (no request written) and `publish_import_request(...)`. Order: `stage_reference_upload` (copy; the original is never consumed) → normalize → run state `{mode: import, revision, entity, request_id, normalized_pixel_hash, expected_kind}` written to the checkpoint → checkpoint digest computed → `publish_import_request(origin_class=imported_synthetic, origin_tool=…, entity_id=<entity>, request_id=f"import-{entity}-{revision}", source_checkpoint_digest=<digest>)`. Request ids are entity/mode/revision-bound (never a hash prefix); `prepare_reference_import` refuses to overwrite an existing pending request and, under the QC/approval lock, refuses a normalized hash that another entity's pending or approved import already claims (`refuse_conflicting_origin` extended with entity). **The import record binds the character** (R1#13): `import_record` gains `entity_id`; `synthetic_import_receipt` lookups and `_enforce_candidate` require the receipt's `entity_id` to equal the pending character. The request's `source_checkpoint_digest` is the digest of the checkpoint holding the run state. Print the command; stop.
2. Next invocation resumes ONLY the tuple in run state (mode, normalized hash, request id, expected receipt kind) under the same five recovery states as D20.1 step 6 (missing → republish after hash check; pending → wait; done → finalize; declined → consume; mismatch → fail closed): `finalize_reference_import`, then the imported candidate is **judged like any other** (R1#4: an "import" is just a file the agent could have produced; the judge catches pipeline mistakes routed around it, and a human override remains available), then the single-candidate pending packet (`imported_image_ref` + `qc_receipt_id`), checkpoint `awaiting_human`, `headshot_request`; print the command; stop.

**Mode B — casting inspiration.** Removed from `headshot_run` (R1#9); see D20.1 step 7.

**Mode C — generate (default)**.
1. `tools/prompt_builder.build_prompt(look, role="hero", palette)` once (recipe sealed as today).
2. **Affordability preflight** (R1#16), under the cost transaction: `remaining_hero_attempts × (generation estimate + judge estimate)` must fit under the cap or the run refuses to start or resume.
3. Generate candidates through the governed Seedream `text_to_image` path with `stage: headshots`, `look_refs`, `prompt_recipe`, plain background in a palette hue, `num_images: 1` per call so every candidate has its own reservation, attempt row and receipt. Attempts run inside the D19 pre-submit hook with series key `(entity, role="hero", look_hash, headshot_receipt_id=null, policy_bundle_sha256, builder_policy_sha256, generation endpoint/model, judge provider/model)`. **One cap, one key** (R1#5, #6): `qc.max_hero_attempts` is the ONLY hero limit, counted against a stable **hero budget key** `(project_id, entity_id, look_hash)` = every `attempt_started` row whose series key carries role `hero` and that look, across all subordinate series (builder/model/judge rotations open a new series for reuse semantics but never a new allowance). `lib/qc_receipts.start_attempt` gains `budget_key` + `budget_cap` and refuses when the budget count would exceed the cap; the verifier recomputes the same count.
4. **Judge every candidate** with the `hero` checklist (D20.3). Candidates that fail are not presented; the loop keeps generating until `--candidates` (default 4) **unique passing asset hashes** exist (R1#15: a duplicate output consumes an attempt but not a slot) or the cap is hit. Fewer at the cap is still presented (1..N); zero → `Blocked`, override request on the best failure, same as sheets.
5. Write the pending packet 1.1 (`candidates[].qc_receipt_id`, sealed `prompt_recipe` required) with run state `{mode: select, revision, request_id: f"headshot-{entity}-{revision}", candidate_hashes, expected_kind: headshot}` in the checkpoint metadata, checkpoint `awaiting_human`, digest, then `headshot_request` bound to that digest; `--open` opens the candidates; print the selection command; stop. **Recovery** (R6#3) follows the same five states: a missing request is republished only after re-validating the checkpoint digest, every candidate hash and its QC receipt against the run state; pending waits; done finishes (step 8); declined consumes (step 7); mismatch fails closed.
6. **Durable run state** (R1#11, R2#2): before any stop the command writes `headshots` checkpoint `metadata.run_state[entity] = {mode, revision, normalized_pixel_hash?, request_id, expected_kind}` (no digest of the file it lives in). The checkpoint is written first; its digest is computed afterwards and bound into the gate request's `source_checkpoint_digest` (existing field; the selection gate already hashes the pending checkpoint into the record as `candidates_checkpoint_digest`). A later invocation resumes exactly the run-state tuple: it looks for a receipt of `expected_kind` whose record matches the persisted hash/request, and refuses anything else ("run state names request X; found none / found a different one").
7. **Reject-all** (R1#12): regeneration is allowed only after the command **consumes the declined request** the human produced at the gate (`.gate-requests/declined/<request_id>.json`, bound to the prior checkpoint digest in run state). The note is copied from that declined request's recorded note, never from the CLI; it is logged in the decision log (`category: revision`, verbatim). The prompt never changes; a note asking for a different appearance is refused with "that is a look change: edit the ticket and run look_run --supersede". Regeneration counts against the same hero budget.
8. After the human selects at the gate, the next invocation (or `--finish`) rewrites the packet `state: approved` for this character (approved entries so far + this one, each with `qc_receipt_id`), checkpoint `in_progress` (D18), rebuilds the canon view (`by-entity/<id>/hero.png`), prints `sheet_run.py …` as the next command.

### D20.3 Hero QC policy (the HERO bundle, independent of the sheet bundle)
`lib/sheet_qc/policy.py` gains role `hero` in its own bundle (the verdict/qc schema and `SheetJudge` accept it; `sheet_run` still refuses it as a sheet role):

| id | question | severity |
|---|---|---|
| single_subject | Exactly one person, no second face or reflection? | fail |
| bust_front | A head-and-shoulders portrait facing the camera, both eyes visible? | fail |
| neutral_expression | A neutral or near-neutral expression, mouth closed or naturally parted? | fail |
| plain_background | A plain, uncluttered background with no scenery, text or props? | fail |
| no_occlusion | Face unobstructed: no hands, glasses, hat, mask, hair across the eyes? | fail |
| hair_matches | Does the hair match the described hair? (evidence: look `hair`) | fail |
| age_matches | Does the apparent age fall in the described band? (evidence: look `age_band`) | warn |
| build_matches | Does the visible build match the described build? (evidence: look `build`) | warn |
| no_text | Free of text, watermark, logo? | fail |
| photoreal_or_treatment | Rendering style consistent within the candidate (no half-illustrated face)? | warn |

Evidence kinds gain `look_hair`, `look_age_band`, `look_build` (text from the signed active look). Local rules for `hero`: square or portrait, long edge ≥ 1024, no alpha. The hero bundle is required ONLY for projects migrating to / running 1.4; 1.3 projects pin the sheet bundle alone and nothing about them changes (R3#1). Golden tests pin the sheet bundle's hash and the byte-identity of the legacy director file.

**Two verifiers over one rule set** (R1#3, R2#4): `lib/headshot_verify.py` has
- `verify_headshot_candidate(project_dir, entry, candidate, *, active_look, config, pin)` — selection time, full ImageRef available: lineage, look binding, sealed recipe (required for generated; forbidden for imported), import-receipt entity binding (R1#13), and under 1.4 `require_candidate_qc` (passing or overridden hero verdict for that exact asset, look, policy bundle and judge, inside a compliant attempt chain within the hero budget). Callers: checkpoint validation of any `headshot_packet` (pending and approved), the gate's `headshot_candidates`/`_enforce_candidate`, and the gate's transactional `pre_commit_check`.
- `verify_active_headshot(project_dir, record, *, active_look, config, pin)` — downstream, from the SIGNED record only: the record (1.4) carries `generation_receipt_id` (or `import_receipt_id`), `prompt_recipe_sha256`, `qc_receipt_id`; the verifier reloads those receipts by id, re-checks look binding, recipe hash, entity binding and the QC verdict chain. Caller: `lib.headshots.verify_headshot_ref` (every sheet call and every sheet verification). Both share the same rule functions; only the input shape differs.

**The relied-on receipts are signed into the headshot record** (`headshot_record` 1.4 gains `generation_receipt_id | import_receipt_id`, `qc_receipt_id`, `record_version: "1.1"`), so a later config/look change is detectable and the TOCTOU window closes as it did for sheets.

**Judge and series for role `hero`** (R1#8): `SheetJudge` and `verify_series_against_receipt` gain an explicit `role == "hero"` branch — `headshot_asset_id`/`headshot_receipt_id` must be **null** (no headshot exists yet; the hero is what is being chosen) and the generation receipt must carry `look_refs` for the entity and **no** `headshot_ref`; sheet roles keep the existing branch unchanged. For an imported candidate the "generation receipt" is the imported receipt (`generator_kind: imported`, no recipe): the series key's `builder_policy_sha256` is the literal `"imported"` sentinel and `generation_endpoint/model` are `"imported"`; the verifier accepts that shape only when the receipt is `imported` and its import receipt names this entity.

### D20.7 Migration 1.3 → 1.4: legacy heroes (R2#3)
An active headshot approved under 1.3 has no QC receipt and a 1.0 record. Two paths, both explicit, neither silent:
- **Grandfather = adjunct attestation, not supersession** (R4#3): `scripts/headshot_run.py --project <slug> --entity <id> --grandfather` judges the active legacy hero under the hero bundle (an attempt in the hero budget, `role: hero`, imported/generated sentinel per its receipt), then writes a `headshot_grandfather` gate request; the human signs a receipt whose record binds `{entity_id, legacy_headshot_receipt_id, asset_id, look_hash, qc_receipt_id}` (new approval kind, envelope `{attests_receipt_id: legacy}`; it is NOT a `headshot` receipt and does not enter the headshot supersession chain, so the legacy receipt stays the chain tip and every existing sheet's `approval_receipt_id` stays current). `verify_active_headshot` accepts a 1.0 record only when a valid grandfather receipt attests exactly that tip; a later `headshot` supersession retires both. **Coverage is enforced at every point** (R3#4): `prepare_migration_request` refuses to write a 1.4 request, the gate's `_construct_pipeline_migration` refuses to construct it, and its transactional `pre_commit_check` re-derives it under the consumed token, unless every active hero of a cast character has a currently valid grandfather receipt (or a 1.1 record). `--grandfather` itself runs under pin 1.3 with config 1.2 (the judge needs the hero bundle and the hero cap; `qc_call_context` accepts pin 1.3 for role `hero` when the attempt is a grandfather attempt, flagged in its series key).
- **Re-approve**: run `headshot_run` normally with `--replace`; the new 1.1 record supersedes the legacy one.
`active_headshots()` is unchanged (the tip is what it always was); `verify_active_headshot` is where 1.4 demands a 1.1 record or a grandfather attestation of the tip.

## Key decisions & tradeoffs
- **Three commands, three gates, one entity at a time.** Matches D18 and the director skills; the commands are the skills' process sections made executable.
- **Imported heroes are judged too** (reversed after R1#4). An "import" is a file the agent could have produced; exempting it is a bypass. The writer can override a failed item at the gate.
- **The reject-all note never edits the prompt.** Same rule as D19: a note that asks for a different appearance is a look change and goes back through the ticket.
- **Hero attempt cap is its own number and its own key.** Sheets are $0.14 with a 3-attempt cap per role; heroes are $0.07 and need up to 4 passing candidates. The hero budget is counted per (entity, look) across every series so no field rotation refills it.
- **`look_run` is separate from `headshot_run`.** Ratifying a look is a writer's gate with no spend; mixing it into the paid command would let a headshot run start before the look is signed.

3. Bloodless's $100 cap has room (spent so far ≈ $1.85).
